# Ръководство за работа

Това е практическото ръководство за ежедневна работа с Desktop Settings, Web интерфейса и нормален CVRP рън. За точните HTTP заявки виж [HTTP API и Web интерфейс](API_AND_WEB.md), а за solver настройките — [Решители, цели и ограничения](SOLVERS_AND_CONSTRAINTS.md).

## 1. Начини за стартиране

От source директорията:

```powershell
.\Settings.bat
.\start_cvrp.bat
.\start_api_server.bat
.\start_api_server_hidden.bat
```

В готов build стартирай същите `.bat` файлове от `dist` директорията. Те избират правилния режим на `Bizant.exe`. Разпространява се цялата `dist` папка, защото допълнителните solver-и работят с companion worker-и.

Режимите са:

| Режим | Предназначение |
|---|---|
| `Settings.bat` | Преглед и постоянно записване на настройките в `config.py`. |
| `start_cvrp.bat` | Един локален рън с текущия вход и текущия `config.py`. |
| `start_api_server.bat` | HTTP API и Web GUI с видим конзолен прозорец. |
| `start_api_server_hidden.bat` | Същият сървър без видим CMD прозорец. |
| `/tsp` | Бързо преподреждане на текущ маршрут на един шофьор; не разпределя между бусове. |

## 2. Desktop Settings

Основните бутони са:

- **Провери** — валидира въведените стойности, без да ги записва.
- **Запази** — записва настройките в `config.py`.
- **Запази и затвори** — записва и затваря прозореца.
- **Запази и стартирай** — записва и стартира нормален рън.

Преди всяко записване се създава timestamp backup в `config_backups`. Добавени/редактирани депа, зони и бусове не са постоянни, докато не бъде натиснат бутон за записване.

### 2.1 Входни данни

Източникът е:

- `http_json` — програмата извиква настроения Bizant/HTTP endpoint;
- `excel` — програмата чете зададения файл и лист.

За HTTP вход се настройват URL, метод, `cmd`, дата, `Sklad`, `DoneFlag`, допълнителни query параметри, timeout и имената на полетата. За Excel се настройват пътят и имената на колоните.

Основните данни за клиент са:

| Данни | Типично HTTP поле | Поведение |
|---|---|---|
| ID | `IdCust` | Идентификатор на клиента. |
| Име | `CustName` | Показва се в карти и отчети. |
| GPS | `GPS` | `latitude,longitude`; невалидните координати правят заявката необслужена. |
| Обем | `Volume` | Участва в капацитета. |
| Документ | `IdDoc` | Пази се в отчетите. |
| Платежен документ | `IdPlasDoc` | Използва се при `setData`. |
| Склад | `IdSkld` | Използва се при складова логика и необслужени заявки. |
| Работно време | `WorkTime` | Един или няколко времеви прозореца. |
| Коментар | `DeliveryComment` | Показва се на шофьора; не променя оптимизацията. |
| Обслужване | `ServiceTimeMinutes` | По желание; заменя времето от буса само за този клиент. |
| Задължителен | `Mandatory` | `true`/`1`/`да` забранява пропускането на този клиент. |

Ако клиентското време за обслужване липсва, е празно или е невалидно, се използва `service_time_minutes` на конкретния бус.

Задължителните клиенти резервират наличния предварителен капацитет преди optional клиентите. Ако mandatory редът е невалиден, клиентът няма GPS, не се побира в никой бус или всички задължителни клиенти не се побират в общия дневен капацитет, програмата връща грешка. Тя никога не го пропуска при parsing, не го мести тихо към склада и не приема solver резултат, в който липсва или е дублиран.

#### Няколко работни прозореца

Поддържат се прозорци на отделни редове:

```text
08:00-13:00
16:00-18:00
```

В JSON новият ред трябва да бъде escaped като `\n`:

```json
{
  "WorkTime": "08:00-13:00\n16:00-18:00"
}
```

Не изпращай буквален необработен control character в JSON string. Програмата има tolerant decoding за някои външни отговори, но валидният JSON е надеждният формат.

#### Групиране на документи

При включено `enable_customer_document_grouping` редове със същия клиентски ID и същия GPS стават едно посещение. Обемът се събира, а оригиналните документи се пазят за отчети и отделни `setData` операции. При изключена настройка всеки документ е отделен стоп.

### 2.2 Превозни средства

Всеки ред описва тип/група физически бусове:

- стабилен `config_id`, тип, име, активност и брой;
- капацитет на един курс;
- fixed cost за използване;
- максимални километри за деня;
- максимално работно време за деня;
- максимален общ брой клиенти за деня;
- стандартно време за обслужване;
- начало на работния ден;
- начално депо;
- крайна точка;
- депо и време за презареждане между курсовете.

Началната точка се избира измежду създадените депа. Празна крайна точка означава връщане в началното депо. Reload точката по подразбиране е началното депо.

`count > 1` създава няколко физически буса със същите правила. Името се разширява с пореден номер в картите и отчетите.

#### Втори курсове

Глобалната настройка **Втори курсове** разрешава един физически бус да се върне за презареждане и да излезе отново. Броят курсове не се задава предварително. Solver-ът може да добавя курсове, докато са изпълними общите дневни ограничения.

- Капацитетът важи за всеки отделен курс.
- Работното време, километри и клиенти важат общо за физическия бус за целия ден.
- Между два курса се начислява `reload_time_minutes`.
- Първият курс няма начално презареждане, а последният няма допълнително презареждане след края.
- Всеки курс получава отделен output номер, но вътрешният `vehicle_key` остава общ за физическия бус.
- Индивидуалната карта е една за физическия бус и има филтър за курсовете; при избран курс се показват неговите клиенти.

VROOM 1.15 не поддържа този свързан модел и изисква вторите курсове да са изключени. Ограниченията на VRP-Rust са описани в solver справочника.

### 2.3 Предварителна оптимизация/склад

Складовата стъпка работи преди solver-а. Тя може да отделя заявки според максимален клиентски обем, капацитет, сортиране по обем и разстояние. Такива заявки не са „пропуснати от solver-а“ — те са класифицирани предварително за складова обработка.

При необяснимо липсващ клиент първо провери дали не е:

- без валиден GPS;
- с нулев/невалиден обем;
- групиран с друг документ;
- отделен от складовата логика;
- върнат като необслужен поради ограниченията.

### 2.4 Solver

Desktop GUI позволява избор между:

- `pyvrp` — стабилен PyVRP 0.13.x (минимум 0.13.4);
- `pyvrp_experimental` — изолиран PyVRP 0.14 worker;
- `or_tools` — OR-Tools;
- `vroom` — official VROOM 1.15 worker;
- `vrp` — експериментален VRP-Rust 1.24 worker.

Общите настройки са objective `distance/time`, време за търсене, работни прозорци, разрешено пропускане и втори курсове. При смяна на solver Desktop и Web GUI автоматично скриват чуждите панели и показват само неговите фини настройки: PyVRP quality/penalties, допълнителния 0.14 worker, OR-Tools strategy/LNS/GLS и списъците за паралелни стратегии, VROOM threads/exploration или VRP-Rust threads/generations. Скритите стойности се пазят и се появяват отново при връщане към solver-а.

### 2.5 Локации, депа и зони

#### Депа

Може да има главно депо, Враца и произволен брой именувани допълнителни депа. След записване имената им се използват в избора за начално и reload депо на бусовете.

#### Основна център зона

Поддържа:

- `circle` — център и радиус;
- `polygon` — списък от точки или чертане на Leaflet карта.

Тя управлява center bus приоритети/отстъпки и наказанията за други типове бусове.

#### Допълнителни център зони

Всяка зона има име, активност, `circle/polygon`, приоритетни типове, ограничени типове, отстъпка, outside penalty и индивидуални vehicle penalties. Динамично добавените зони се подават и към паралелните solver работници.

**Показвай на картата** управлява само визуализацията. Скриването на зоната не изключва правилото ѝ. За допълнителна зона използвай `enabled=false`; legacy основната зона се изключва чрез едновременно изключване на приоритетите и ограниченията.

#### Трафик зони

Трафик зоната умножава времето за движение в определения кръг. `show_on_map` отново е само визуална настройка и не изключва множителя.

### 2.6 Изходни данни

Поотделно могат да се включват следните output групи:

- карти — един `enable_interactive_map` switch генерира общата и индивидуалните карти заедно;
- Excel отчети;
- CSV;
- PNG графики;
- upload на индивидуалните карти.

Поддържат се Folium/Esri и Google Maps. Google режимът изисква API ключ. Output настройките включват директории, имена, bus numbering, специално center bus номериране и отделен съботен префикс.

Общата карта не показва вътрешния `route_id` или пореден route номер в popup заглавията. Индивидуалната карта запазва course metadata и филтъра за отделните курсове на физическия бус.

При `/run_saturday` датата е съботата от текущата седмица, нормалното bus numbering използва съботния префикс/брой цифри, а към имената на картите и Excel файловете се добавя `_събота` след датата. Ако специалното center номериране е включено, CENTER_BUS продължава да използва серията от `center_bus_numbering_start_id`; тя има предимство пред съботния prefix.

### 2.7 Разширени

Тук са събрани:

- HTTP API адреси, key и endpoint-и;
- Web GUI и потребители;
- TSP настройки, field mapping, truck профили и дневен отчет;
- `setData`/`makeGroup`;
- Windows Task Scheduler;
- вграденото кратко ръководство.

Web потребителите се управляват от Desktop Settings и се записват веднага в защитеното хранилище `data/web_gui_auth.json`; общият бутон **Запази** не е необходим за добавяне/изтриване на потребител.

## 3. Web интерфейс

Web GUI обикновено е на настроения `api.web_gui_endpoint`, например `/hell`. Изисква потребител и парола, session cookie и CSRF защита за променящите операции.

В него има четири основни действия, които не трябва да се смесват:

| Действие | Какво променя |
|---|---|
| Стартирай без запис | Пуска изолиран рън с временните solver/output/`setData` стойности; не записва `config.py`. Входът, routing-ът, депата, зоните и бусовете се вземат от последно записания config. |
| Запази глобалните настройки | Записва позволените общи solver/output/`setData` полета в `config.py`, без списъка с бусове. API host/endpoints и Web потребителите се управляват от Desktop GUI. |
| Запази бусовете | Подменя само `VehicleConfig` редовете в `config.py`; останалите настройки не се засягат. |
| Отхвърли промените и зареди глобалните | Презарежда Web формата от последно записания `config.py`, без да записва текущите редакции. |

Незаписаните редакции по бусовете не участват в **Стартирай без запис** — първо използвай отделното записване на бусовете. В Web формата стартът е избор на именувано депо, а custom end/reload стойностите са GPS полета.

Кодът пази legacy `web_gui_run_defaults_json` и вътрешен `/api/run-defaults`, но текущата Web страница няма активен бутон за него и текущият старт не прилага този preset. Не го използвай като работен слой настройки.

Web GUI може още да показва статус и последни логове, да спре активния child process, да излезе от сесията и да поиска контролирано спиране на сървъра.

## 4. Препоръчан ежедневен workflow

1. Провери входната дата, `Sklad` и `DoneFlag`.
2. Провери активните бусове, депата и дневните лимити.
3. Провери solver-а, objective-а и времето за решаване.
4. Провери output и дали `setData` е включено.
5. При първи тест изключи реалния `setData` upload.
6. Стартирай ръна и следи статуса/лога.
7. Провери необслужените клиенти и причините им.
8. Прегледай индивидуалните карти, курсовете и Excel отчета.
9. Включи интеграционното изпращане едва след проверка на резултата.

## 5. Важни предупреждения

- Не редактирай едновременно `config.py` от Desktop и Web GUI.
- Не копирай само `Bizant.exe`; worker директориите са част от build-а.
- При bind към `0.0.0.0` настрой API key и използвай HTTPS reverse proxy за Web GUI извън доверена LAN.
- Token-и и API ключове не трябва да се публикуват в примерни JSON-и или Git.
- Един основен CVRP рън може да е активен в даден момент; втори trigger връща `409 already_running`.
- Скритата на картата зона продължава да влияе на solver-а.
- Невалидното работно време може да бъде игнорирано с warning; валидирай входния формат предварително.
